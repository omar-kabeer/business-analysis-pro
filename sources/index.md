# Source Library Index

What is held in `sources/`, what each item is allowed to govern, and the licence position on each. The rules for using this material are in `skills/skill-upgrader/references/source-protocol.md`. This file is the inventory; that file is the method.

**These standards are conformance criteria, not citation sources.** The system does not quote them. It produces outputs that pass them. A process model is not good because it references BPMN, it is good because it is valid BPMN. A requirement statement is not good because it mentions ISO 29148, it is good because it satisfies the characteristics that standard sets. The library exists so every deliverable can be checked against the standards that govern its artefact type.

The library sits outside the distributable plugin and is excluded from version control by `.gitignore` line 33. Skills cite this material, they do not ship it. Anyone rebuilding the library on another machine works from this index and from `manifest.json`.

**The tables below are generated.** `manifest.json` is the register of record, `naming-convention.md` states the filename and id rules, and `scripts/build-source-index.mjs` rewrites the generated blocks from the manifest. Edit the manifest, then run `npm run sources:index`. Prose outside the generated markers is hand-written and survives regeneration.

`standards-mapping.md` is the curation specification: it maps all thirty-nine skills to the standards they should rest on, with BABOK task anchors and the deliverables produced. Read it before curating anything further.

## How shared sources are held

A standard usually serves several skills. BPMN 2.0 feeds process-modelling and visual-modelling; WCAG feeds ux and prototyping; ISO 24495 feeds communication, executive-review, and natural-prose-editor. Copying a PDF into each skill's folder would create several copies to keep in step, so the file stays once under `standards/` or `practice/` and the mapping lives in the manifest's `skills` array.

This means a skill can be well sourced with an empty papers folder. Read the generated skill table, not the folder listing.

## Authority levels

Every source carries an `authority` value, and it decides what the source is permitted to do.

`normative` means the source gates output. It is the real standard, current enough to rely on, and the artefact types in its `constrains` list must pass it before delivery. Twenty-one sources hold this level.

`supporting` means the source informs method but does not gate. The Kimball techniques paper is the clearest example: authoritative in practice for dimensional design, but not a published standard, so it shapes how we work without being a pass or fail test.

`illustrative` means the source is background only. Lecture slides, marketing white papers, and conference decks sit here. They may not gate anything and they may not be presented as authority.

The distinction matters because the failure mode is silent. A slide deck filed as a standard looks identical to a standard in a folder listing, and a skill built on it will produce confident output backed by nothing. `identityVerified` records whether anyone has actually opened the file and confirmed what it is.

## Licence discipline

Licence position governs redistribution, which is a separate question from authority. `open` covers W3C material and the Scrum Guide. `free-to-obtain` covers most OMG, Open Group, and ISACA downloads: read freely, redistribute never. `licensed-copy` and `restricted` cover BABOK, ISO deliverables, and commercial books, where the copy itself is licensed to one holder. `unknown` means nobody has checked.

Because we conform rather than quote, licence position rarely blocks use. It does still block shipping any of this material with the plugin, which is why `sources/` is gitignored.

## BABOK v3

`babok/babok-3.0-2015.pdf` is the anchor source for every skill and is registered with `"skills": ["*"]`, so it does not appear in the per-skill counts. It sets vocabulary and the artefact set, and it is dated on tooling, agile practice, and data and AI, which reference files should say out loud rather than reproduce.

## Defects found on inspection

Text extraction confirmed what each file actually is. Four were not what their filenames claimed, and under a conformance model that is a serious class of defect rather than a filing error.

`opengroup-togaf-presentation-2003` was filed as the TOGAF standard. It is a 2003 conference slide deck. Business-architecture and architecture were counted as sourced on it, and neither now has a normative standard. This is the largest single gap in the library.

`iiid-24495-document-design-patterns-draft` was filed as ISO 24495 part 2. It is a third-party companion pattern library from the International Institute for Information Design, and a development draft at version 0.6. Demoted to supporting.

`consultingmethodology-pyramid-whitepaper` was filed as a condensed Pyramid Principle. It is a marketing white paper from a consultancy summarising Minto, not Minto. Demoted to illustrative, and the full Minto text supersedes it.

`horvath-crisp-dm-lecture` is university lecture slides, and `datasciencepm-evaluating-crisp-dm` is a vendor white paper. Only `crisp-dm-1.0` is the real consortium document.

Separately, `iso-31000-2018` is the genuine standard but the copy carries a Clarivate Techstreet watermark licensing it to a University of Toronto user and stating that no further reproduction or distribution is permitted. It is not licensed to us. It can serve as a conformance reference internally, but it should be replaced with an owned copy before it underpins client deliverables.

## Where the library is thin

Fourteen skills have no normative standard governing their output, up from ten before inspection. Five are acceptable. `ba-planning`, `business-analysis`, and `solution-evaluation` are BABOK constructs, and BABOK is itself normative for them. `prompt-master` and `orchestrator` have no external standard in existence to conform to.

The other nine are real gaps, and under a conformance model a gap means something specific: the output has no external pass or fail test, so quality rests entirely on our own judgement. `elicitation` and `market-research` want ISO 20252. `document-analysis` and `technical-writer` want ISO/IEC 26514. `information-management` wants ISO 15489. `finance` wants ISO 20022 and an accounting reference. `proposal-writer` wants the APMP standards.

Four of the nine lost their standard on inspection rather than never having had one. `architecture` is the worst affected: TOGAF was its only claimed standard and the file turned out to be a slide deck, so it now has nothing normative. `business-architecture` survives because ArchiMate, BMM, and APQC PCF remain, so it degrades rather than fails. `technical-writer` lost the ISO 24495 part that was not a real part. `product-manager` holds only the Agile Practice Guide, which is supporting rather than normative.

Acquiring the real TOGAF Standard is the highest-value single acquisition remaining, since it restores a normative gate to two skills at once.

The decision on record is that remaining gaps are closed by our own research rather than by further acquisition. That works for method depth. It does not produce a conformance gate, because research we conducted cannot be the independent test our own output passes. Where a skill has no normative standard, the honest position is that its outputs are checked against BABOK and internal rubrics, and to say so rather than imply external conformance.

## Making conformance real

The manifest now records which artefact types each normative standard gates, and the generated table above inverts that into artefact type to governing standard. That is the binding the system needs: a deliverable knows its artefact type, the type resolves to its standards, and those standards decide whether the output passes.

What does not yet exist is the checks themselves. `constrains` says BPMN 2.0 governs process models; it does not yet say what a process model must satisfy to pass BPMN 2.0. Turning each normative standard into a set of testable checks is the next piece of work, and it belongs with the skill upgrade sessions, since extracting obligations from a standard is exactly what the upgrade pass already does for BABOK.

## Adding a source

1. Name the file to the rule in `naming-convention.md`. Lowercase, hyphens, no spaces, version last.
2. Add a record to `manifest.json` with title, publisher, version, tier, path, locator style, licence position, and the skills it serves.
3. Run `npm run sources:index`. It fails on unregistered files, missing paths, bad filenames, id and filename mismatches, and unknown skill names.
4. If the licence position is `unknown` or `verified` is false, settle it before the skill's batch runs.

## Rebuilding this library

Obtain a licensed BABOK v3 PDF and place it at `sources/babok/babok-3.0-2015.pdf`. Acquire the standards listed in the generated table above, name them to the convention, and restore `manifest.json`. Curate journal papers into `sources/papers/<skill-name>/`. Leave `sources/` in `.gitignore`. Nothing here is redistributed with the plugin.
