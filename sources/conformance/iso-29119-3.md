# Conformance checks: iso-29119-3

Source id: `iso-29119-3`
Standard: ISO/IEC/IEEE 29119-3, Software and systems engineering, Software testing, Part 3: Test documentation.
Edition held: First edition, 2013-09-01 (ISO/IEC/IEEE 29119-3:2013(E)).
Publisher: ISO/IEC/IEEE.
Identity: confirmed from the title page on 2026-08-07. First edition 2013. A 2021 second edition exists; the checks below are for the 2013 edition held, cite that edition.
Authority: normative.
Licence: ISO/IEC/IEEE copyright, restricted; paraphrase only.
Modality note: 29119-3 states its conformance and tailoring rules with "shall". It allows the defined content of a document to be tailored, but requires that any omission of a defined information item be justified, recorded with its rationale and risks, and agreed by stakeholders. The content requirements are therefore blocking, with a documented-tailoring escape (see TS-06).
Artefact types constrained: `test-specification`, `acceptance-criteria`.
Owning skills: `acceptance-testing` (primary), `quality`.
Locator style: ISO/IEC/IEEE 29119-3:2013 clause `<n>`.

## How to read this file

Three layers, kept separate: Source (S) with locator, labelled Inference (I), and the Check (C), answerable yes or no from the finished artefact.

## Checks: test-specification

Applies to a test specification (Test Design, Test Case, or Test Procedure Specification).

| Check id | Question (yes = pass) | Severity | Locator | How the reviewer confirms |
| --- | --- | --- | --- | --- |
| ISO29119-TS-01 | Does each test case carry a unique, stable identifier used for traceability? | blocking | 7.3.5.2 | Confirm each test case has a unique id that is not reused or changed. A test case with no id fails. |
| ISO29119-TS-02 | Does each test case specify its preconditions, inputs, and expected results? | blocking | 4.12, 7.3.5 | Confirm all three parts per test case. A test case missing expected results, inputs, or preconditions fails. |
| ISO29119-TS-03 | Is each test case traceable to the test coverage item or test condition it exercises, or to the associated requirement or design in the test basis? | blocking | 7.3.5 | Confirm a trace link per test case. An untraceable test case fails. |
| ISO29119-TS-04 | Does a Test Design Specification identify the features to be tested and the test conditions derived for each feature? | blocking | 7.2, 4.18 | For a design spec, confirm features and their test conditions. Absence fails. |
| ISO29119-TS-05 | Where a defined information item is omitted, is the tailoring justified, recorded with its rationale and applicable risks, and agreed by the relevant stakeholders? | blocking | clause on tailoring (Conformance) | Confirm any omission carries a recorded, agreed justification. An unexplained omission fails. |
| ISO29119-TS-06 | Do expected results give expected values with tolerances where appropriate? | advisory | 7.3.5 | Check expected outputs are specified with tolerances where relevant. Advisory. |
| ISO29119-TS-07 | Are test conditions, coverage items, and test cases prioritised where priority is needed? | advisory | 7.2, 7.3 | Look for priority attributes. Advisory. |

## Checks: acceptance-criteria

Applies to an acceptance criterion (the condition under which a requirement or feature is accepted, from which a test can be derived).

| Check id | Question (yes = pass) | Severity | Locator | How the reviewer confirms |
| --- | --- | --- | --- | --- |
| ISO29119-AC-01 | Is the acceptance criterion expressed in a verifiable way, so a test condition or test case can be derived and a pass or fail determined? | blocking | 7.2.5 (test conditions), 4.28 | Confirm the criterion is testable. A criterion that cannot be verified fails. |
| ISO29119-AC-02 | Does the criterion define the expected observable result (the predicted behaviour under specified conditions) against which actual results are compared? | blocking | 4.3, 4.28 | Confirm the criterion states an expected, observable outcome. A vague aspiration with no expected result fails. |
| ISO29119-AC-03 | Is the criterion traceable to the requirement or feature it accepts? | advisory | 7.3.5 (traceability) | Look for a trace link to the requirement. Advisory. |

### Provenance, test-specification

- TS-01. S: The information for a test case includes a unique identifier, which is not changed during the test case's lifetime because it is used for traceability (7.3.5.2). I: none.
- TS-02. S: A test case is a set of preconditions, inputs (including actions where applicable), and expected results (4.12); the Test Case Specification defines preconditions, inputs, and expected results for each test case (7.3.5). I: none.
- TS-03. S: The information for a test case includes traceability to the test coverage item it exercises or references to the associated requirements or design in the test basis (7.3.5). I: none.
- TS-04. S: The Test Design Specification identifies the features to be tested and the test conditions derived from the test basis for each feature (7.2, 4.18). I: none.
- TS-05. S: Where an information item defined in Clauses 5, 6, and 7 is not prepared, justification shall be provided; all tailoring decisions shall be recorded with their rationale, including applicable risks, and agreed by the relevant stakeholders (Conformance and tailoring clause). I: We gate omissions on a recorded, agreed justification.
- TS-06. S: Expected results provide the expected values, with tolerances where appropriate, for each required output (7.3.5). I: Advisory precision check.
- TS-07. S: Priority may be defined for test conditions, coverage items, and test cases, higher priority run earlier (7.2, 7.3). I: Stated as "if needed", so advisory.

### Provenance, acceptance-criteria

- AC-01. S: A test condition could be a reference to a requirement if the requirement is expressed in a verifiable way, that is if it includes an identifiable acceptance criterion (7.2.5 note); a test result indicates whether actual results correspond to expected results (4.28). I: We read a valid acceptance criterion as one that is verifiable enough to derive a test and judge pass or fail.
- AC-02. S: Expected results are the observable predicted behaviour of the test item under specified conditions (4.3); the test result compares actual to expected (4.28). I: We gate the criterion on stating an expected observable result.
- AC-03. S: Traceability links test cases to the associated requirements in the test basis (7.3.5). I: Advisory trace check.

## Coverage

- `test-specification`: 5 blocking checks (TS-01 to TS-05), 2 advisory (TS-06, TS-07).
- `acceptance-criteria`: 2 blocking checks (AC-01, AC-02), 1 advisory (AC-03).

Both constrained artefact types carry blocking checks (forward cross-check satisfied). Every check maps to a declared artefact type, no orphans. No other normative source constrains these two types, so no conflict. Note: `acceptance-criteria` is related to `requirement-statement` verifiability under `iso-29148` (RS-05); the two are consistent, one testing the requirement's verifiability and the other the criterion derived for acceptance.
