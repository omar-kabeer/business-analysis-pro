# Conformance checks: iso-27002

Source id: `iso-27002`
Standard: ISO/IEC 27002, Information security, cybersecurity and privacy protection, Information security controls.
Edition held: Third edition, 2022-02 (ISO/IEC 27002:2022(E)).
Publisher: ISO/IEC.
Authority: normative.
Identity: confirmed from the title page on 2026-08-07. Third edition 2022. The manifest recorded the version as "27002"; it is the 2022 third edition.
Licence: ISO/IEC copyright, restricted; paraphrase only.
Modality note: ISO/IEC 27002 is a reference set of controls and a code of practice. It states its controls and guidance with "should", and it explicitly lets organizations disregard any of the attributes. It is not a certifiable "shall" standard. The blocking severities below are our house gate for a control that claims to follow the 27002 layout; the attribute checks are advisory because 27002 makes attributes optional.
Artefact types constrained: `security-control`, `compliance-matrix`.
Owning skills: `regulatory-compliance` (primary), `risk-analysis`.
Locator style: ISO/IEC 27002:2022 clause `<n>`.

## How to read this file

Three layers, kept separate: Source (S) with locator, labelled Inference (I), and the Check (C). Severity here reflects a house-gate decision, not "shall" verbs (see the modality note).

## Checks: security-control

Applies to a single information security control as documented in our deliverables.

| Check id | Question (yes = pass) | Severity | Locator | How the reviewer confirms |
| --- | --- | --- | --- | --- |
| ISO27002-SC-01 | Does the control have a title, a control statement (what the control is), and a purpose (why it should be implemented)? | blocking | 4.3 | Check the three layout elements are present. A control with no purpose, or no stated control, fails. |
| ISO27002-SC-02 | Is the control statement (the "what") distinct from the implementation guidance (the "how")? | blocking | 4.3 | Confirm the control does not collapse what-to-do and how-to-do-it into one blur. A control written only as how-to fails. |
| ISO27002-SC-03 | Is the control classified by attributes drawn from the 27002 taxonomy (control type; information security properties; cybersecurity concepts; operational capabilities; security domains), using the defined attribute values? | advisory | 4.2 | Check an attribute table with values from the defined sets. Advisory: 27002 lets an organization disregard attributes. |
| ISO27002-SC-04 | Where the control-type attribute is used, is its value one of Preventive, Detective, or Corrective? | advisory | 4.2 a) | Check the control-type value is valid. Advisory. |
| ISO27002-SC-05 | Is implementation guidance (the "how") provided? | advisory | 4.3 | Look for guidance text. Advisory: some controls need little guidance. |

## Checks: compliance-matrix

Applies to a control-compliance matrix (for example a Statement of Applicability) insofar as it draws on ISO/IEC 27002 controls. The Statement of Applicability structure itself is gated by `iso-27001-2022`; the checks here add the 27002-specific identification and classification.

| Check id | Question (yes = pass) | Severity | Locator | How the reviewer confirms |
| --- | --- | --- | --- | --- |
| ISO27002-CM-01 | Is each control that derives from ISO/IEC 27002 identified by its 27002 reference (clause number and title)? | blocking | 4.1, Clauses 5 to 8 | Confirm 27002-sourced controls cite their clause and title. A control claiming 27002 origin with no reference fails. |
| ISO27002-CM-02 | Do the matrix's controls carry 27002 attribute values (for example control type or information security properties) to support filtered views? | advisory | 4.2 | Look for attribute values on the controls. Advisory, since attributes are optional. |

### Provenance, security-control

- SC-01. S: The layout for each control contains a control title, an attribute table, the Control (what the control is), the Purpose (why it should be implemented), Guidance (how), and Other information (4.3). I: We gate on title, control, and purpose as the essential layout, and treat attributes and guidance as advisory because 27002 states them as optional or as aids.
- SC-02. S: The layout distinguishes Control (what) from Guidance (how) (4.3). I: We gate on that separation.
- SC-03. S: Each control has been associated with five attributes (control type; information security properties: Confidentiality, Integrity, Availability; cybersecurity concepts: Identify, Protect, Detect, Respond, Recover; operational capabilities; security domains), but organizations can disregard one or more attributes (4.2). I: Advisory because the standard makes attributes optional.
- SC-04. S: Control type values are Preventive, Detective, Corrective (4.2 a). I: Advisory validity check on a used attribute.
- SC-05. S: Guidance describes how the control should be implemented (4.3). I: Advisory.

### Provenance, compliance-matrix

- CM-01. S: The document structures controls into Organizational (Clause 5), People (6), Physical (7), and Technological (8), each with a clause number and title (4.1, Clauses 5 to 8). I: We gate 27002-sourced controls in a matrix on citing that reference so the mapping is auditable.
- CM-02. S: Attributes can be used to filter, sort, or present controls in different views (4.2). I: Advisory, attributes optional.

## Not-testable obligations

| Obligation (paraphrase) | Locator | Why not testable on a finished artefact |
| --- | --- | --- |
| The individual guidance under each of the 93 controls (Clauses 5 to 8). | 5 to 8 | Guidance on how to implement each control in the environment; evidenced by operational practice, not by inspecting a control definition or matrix. |
| Controls should be selected based on risk assessment and business value against cost. | 0.1, and general | A selection judgement made during risk treatment (governed by ISO/IEC 27001 6.1.3), not a property of the delivered control artefact. |
